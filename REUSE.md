# Reusing Varath's code in another project

This is a map for a **different game** that wants to lift parts of Varath. It's
written for whoever (human or AI assistant) is building the new game, so they
can find the genuinely portable pieces fast instead of reading 36k lines.

## The one thing to understand first

**Varath has no asset files.** There is not a single `.png`, `.jpg`, `.svg`,
`.mp3`, `.wav`, `.ogg`, or font file in the whole repo. Everything you see and
hear is **generated by code at runtime**:

- **Sprites & world art** — drawn as shapes on an HTML5 canvas.
- **Item / UI icons** — generated as SVG strings.
- **Music & sound effects** — *synthesised live* in the browser with the Web
  Audio API. No recordings.
- **Fonts** — system fonts only.

So "reuse the assets" really means **reuse the little engines that draw and
synthesise them**. The good news: they're self-contained TypeScript with
**zero runtime dependencies** (the whole project depends only on `typescript`
and `vite` at build time), so dropping a module into another Vite/TS project is
usually just a copy-paste plus a type tweak.

## Stack

- TypeScript (strict, `exactOptionalPropertyTypes: true`), ES modules.
- Vite for dev/build. No framework, no runtime libraries.
- Architecture: a **pure core** (`src/core`) that never touches the DOM, driven
  by a thin **client** (`src/client`) that renders and feeds it input. Content
  (items, monsters, map, quests…) is plain data in `src/content`.

## Reuse tiers

### Tier 1 — drop-in (≈zero coupling)

These import nothing from Varath (or only a trivial type) and work in any
browser TS project as-is.

| File | What it is | Coupling |
|------|-----------|----------|
| `src/client/audio.ts` | A full **procedural audio engine**: an `AudioManager` singleton that synthesises SFX and layered ambient/boss music from Web Audio nodes — no files. Has a compressor, master mix, per-scene ambient beds, and creature "voices". | **None** (no imports). The `Sfx` / `SceneKey` / `CreatureVoice` string unions are Varath-named — rename the cases, keep the synth engine. |
| `src/client/glyph.ts` | Maps short names / emoji to inline **SVG glyphs** (`glyph("boot")`, `iconize(str)`). A tiny icon system with no font dependency. | **None**. |
| `src/client/pathfinding.ts` | Generic **A\* grid pathfinding**: `findPath`, `pathToAdjacent`, `pathToWithin`. Works on any walkability callback. | Only imports the `Vec2` type (`{x,y}`) — define your own, delete the import. |
| `src/client/storage.ts` | **Multi-account localStorage save slots**: list/select accounts, read/write/clear saves. | **None**. Generic browser save plumbing. |

### Tier 2 — portable with light adaptation

Useful engines that touch a Varath type or two. Copy them and either reshape the
type or pass a minimal object.

| File | What it is | What to adapt |
|------|-----------|----------------|
| `src/client/itemIcon.ts` | **Procedural item-icon generator.** `itemIconSVG(def)` classifies an item by name/tags → picks a shape family (blade, potion, bone, tooth, fish, ore…) → returns a 32×32 SVG. Hundreds of distinct icons from code. | Takes an `ItemDef`. Feed it a minimal `{ id, name, tags? }`-shaped object, or copy the `ItemDef` fields it actually reads. |
| `src/client/avatar.ts` | **Canvas humanoid renderer** with walk/attack/tool animation: `drawAvatar(...)`, `drawTool(...)`, plus palettes (`SKINS`, `HAIRS`, `CLOTH`) and style tables (hair/facial/tops/legs/shoes) and `DEFAULT_APPEARANCE`. A whole customisable paper-doll system. | Imports the `Appearance` type and `gearLook.ts`. Bring both; simplify `Appearance` to the fields your game has. |
| `src/client/gearLook.ts` | Resolves equipped items → a **visual "gear look"** (metal tints, armour style: plate/leather/robe) for the avatar to draw. | Coupled to Varath's item/equip types. Reusable as the *pattern* for "equipment → how the character looks"; adapt the lookup. |
| `src/core/duelCore.ts` | A **deterministic lockstep fight simulator** — pure, seeded, identical on every machine. Also the home of the **`mulberry32` seeded RNG** (see below), which you'll want regardless. | Self-contained logic but models Varath combat. Lift the RNG and the lockstep pattern even if you rewrite the rules. |

**The seeded RNG** (copy this anywhere — it's the backbone of deterministic
gameplay and testing):

```ts
// mulberry32 — tiny, fast, identical on every machine. Seed with any int.
function mulberry32(seed: number): () => number {
  let s = seed | 0 || 1;
  return () => {
    s = (s + 0x6d2b79f5) | 0;
    let t = s;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
```

### Tier 3 — reference / technique (not drop-in)

Big, Varath-specific files. Don't copy wholesale, but they're worth reading for
*how a thing is done* — lift the technique, not the file.

| File | Techniques worth stealing |
|------|---------------------------|
| `src/client/render.ts` (7.8k lines) | **Camera** (`Camera` interface, world→screen), **terrain chunk caching** (static ground pre-rendered to offscreen canvases, `drawImage`'d each frame — big perf win), **corner-blended tiles** so terrain types melt together, **biome noise** (`biomeAt`), procedural vegetation/particles/ember/weather, day-night lighting, `TILE = 40` grid convention. |
| `src/core/worldCore.ts` (7.6k lines) | The **pure reducer architecture**: `createWorld(content, spawn, ctx)`, `applyIntent(state, content, intent, ctx)`, `tick(state, content, ctx)`. All game state changes go through typed **intents**; the core is pure (no DOM, no `Date.now()` — time/rng come in via `Ctx`). This is the single most valuable *pattern* to carry over. |
| `src/core/types.ts` (2.9k lines) | How to model a whole game as data + a closed `intent` union. Good reference for structuring your own `types.ts`. |
| `src/client/hud.ts` (2.3k lines) | Building a **DOM+canvas HUD** by hand (panels, tabs, bars) with no UI framework — measuring/pinning panels, tab docks, accessibility toggles. |
| `src/client/loop.ts` (2.9k lines) | The **game loop** wiring: input → intents → `tick` → `drawWorld`, plus how all the UI modules are constructed and fed. |

## The architecture pattern (the most reusable idea)

Even for a very different game, this shape is worth copying:

1. **`Ctx`** carries the impure inputs: `{ now, rng, epoch }`. The core never
   calls `Date.now()` or `Math.random()` directly — everything comes through
   `Ctx`. That's what makes the whole game **deterministic and testable**.
2. **Pure core**: `createWorld` builds initial state; `applyIntent` handles one
   player action; `tick` advances time. No DOM, no I/O.
3. **Intents** are a typed union (`MoveIntent`, `InteractIntent`, …). The client
   only ever *dispatches intents*; it never mutates game state directly.
4. **Content is data** (`src/content/*.ts`): items, monsters, map, quests are
   plain objects, not code. Swappable without touching the engine.

Because the core is pure and seeded, Varath is verified with **driven-intent
probes**: bundle the core with esbuild, run it in Node with a `mulberry32` seed,
fire scripted intents, and assert on the resulting state — no browser needed.
Reuse that testing approach; it's cheap and catches a lot.

## How to pull this into the new build

The new game should be **its own repo** (don't build it inside Varath). Then, in
the new project's Claude Code session:

1. Make sure the session has **read access to `trevorvail3/world`** (add it as a
   readable repo if it isn't already).
2. Ask for specific modules, e.g.:
   > "Read `REUSE.md` in `trevorvail3/world`, then copy `audio.ts`, `glyph.ts`,
   > `pathfinding.ts`, and `itemIcon.ts` into this project and adapt the types
   > to our game."
3. For anything in Tier 3, ask for the *technique* ("show me how Varath does the
   camera / terrain caching and adapt it"), not a raw copy.

Everything here is your own code across your own projects, so reuse is entirely
fine. Start from the Tier 1 list — those are free.
